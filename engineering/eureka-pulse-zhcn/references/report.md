# 月报与周报

## 目标与输入

- **目标**：取得指定完整自然月或自然周的数据，生成并交付独立 HTML 简报。默认生成上一个完整自然月，自动读取包含目标月的最近十二个完整自然月；已有简报的周报结合最近八个完整自然周的已有结果展示变化。
- **输入**：个人 Pulse 的真实 ID、完整配置、本次 `report_request` 和执行目录。`report_request` 保存报告周期与生成或查看目的；配置中的周计划继续保持。
- **公共规则**：读取 [MCP 与文件管理](mcp.md)及 [HTML 生成](html.md)。

## 执行步骤

### 步骤一：确定周期与配置

1. **取得完整配置**：已有监控调用[目标定位入口](mcp.md#目标定位与配置来源)取得当前配置；创建交接使用创建后 `get_mcp_brief_info` 的完整原始响应。
2. **选择报告周期**：用户没有明确报告周期时使用 `month`；要求月报且没有指定月份时使用上一个完整自然月。明确要求周报、上周或具体周次时使用 `week`。只提供六位数字且无法依据上下文确定周期时询问必要信息。`scheduled_run_enabled` 和配置的 `period_type=week` 不用于推断本次报告周期。
3. **计算目标日期**：使用以下命令生成 `target.json`，接收程序返回的起止日期、`period_type` 和六位 `period`。日期使用当前运行环境明确提供的用户时区；没有用户时区时采用机器本地时区并记录。指定月份或周次时增加 `--period <六位编码>`；只允许完整且已经结束的目标周期。

   ```bash
   python scripts/monitor.py period --pulse-id <真实ID> --today <用户当地日期YYYY-MM-DD> --output <target.json>
   ```

   - **默认月报**：命令默认 `--period-type month`，月份编码为 `YYYYMM`，覆盖第一日至最后一日。以用户当地日期 `2026-11-18` 为例，默认目标为 `202610`，日期为 `2026-10-01` 至 `2026-10-31`。
   - **明确周报**：增加 `--period-type week`；未指定周次时计算上一个完整自然周，日期为周日至周六，编码为 `YYYYWW`。
4. **核对周期含义**：周报默认使用 `first-sunday`，即当年第一个周日开始的周为第一周；该规则已由个人 Pulse 的真实响应日期核实。当前服务明确提供其他规则时显式传入对应 `--week-rule` 并记录依据。月报通过目标月份核对起止日期，周编码规则不参与月份计算。查询结果起止日期必须与目标一致，跨年周期也执行同样检查；日期不一致时停止依赖步骤，核实编码后重新查询，不能直接运行错误日期对应的周期。

### 步骤二：取得完整目标期资料

1. **查询目标期结果**：按 [MCP 请求语言](mcp.md#mcp-请求语言)核验本次实际调用连接，确认详情请求的 HTTP Header 为 `X-Site-Lang: CN`，再调用 `get_mcp_brief_data`。从 `target.json` 取得真实 `pulse-id`、`period_type` 和 `period`，业务参数遵守当前 Tool schema。完整且身份、日期和显示配置一致的数据直接进入步骤三。
2. **处理目标期缺失**：本次要求生成报告且目标为月度（包括默认月报），或本次新建简报需要交付首期结果时，目标期不存在即可按当前目标调用一次运行接口。用户仅查看已有结果时保留缺失状态；已有周报仍按最近八周读取规则处理，只有明确要求生成缺失周次时才触发对应周任务。权限、积分、参数错误、响应不完整及未知错误均不能当作目标期不存在。
   - **月报运行**：同一 MCP 连接实际提供 `run_mcp_month_brief` 时优先使用，仅提交 `pulse-id` 与 `period`；当前连接仅提供 `run_mcp_personal_brief` 时提交同一 ID、`period_type=month` 与 `YYYYMM`。使用当前 Tool schema 检查完整请求。
   - **周报运行**：同一连接实际提供 `run_mcp_week_brief` 时优先使用，仅提交 `pulse-id` 与 `period`；否则调用 `run_mcp_personal_brief`，提交同一 ID、`period_type=week` 与 `YYYYWW`。
3. 每个 `pulse_id + period_type + period` 仅触发一次。`accepted=true` 且返回真实 `run_id` 时保存任务；`accepted=false` 保留拒绝原因，不构造任务 ID。
4. 持续查询同一个 `run_id`。`PENDING`、`RUNNING` 继续等待与查询，并提供必要进度；`FAILED`、`NOT_FOUND` 停止查询该 ID，保存失败及继续条件。
5. `FINISHED` 后通过步骤一已经核验的中文连接调用 `get_mcp_brief_data`，再次读取同一期完整资料并保存原始响应。连接已重新建立或切换时，重新完成 Header 检查。状态响应用于任务状态核实，报告数据使用周期查询返回的完整结果。部分结果、未知错误、分页未完成和生成失败均不能作为完整资料。
6. 同一期已有结果与修改后配置不一致时，核实服务是否支持该期重新生成及结果版本识别。当前说明不足以确认时说明具体限制，保留结果和配置，不重复触发任务。

### 步骤三：准备周期统计与历史

1. **读取月报历史**：月报自动调用[历史比较模块](history.md)，传入完整配置、月度 `target.json` 和执行目录；默认窗口包含目标月及之前十一个完整自然月。步骤二已经取得的目标月响应直接登记，其余月份只查询已有结果。根据历史模块的实际字段与资料检查，至少两个有效月份时支持趋势曲线，缺失月份保持空缺。没有可比历史时，汇总统计范围内已取得的有效资料，展示实际分布。月度 Summary、Insight 与资料始终读取目标月响应，周次收录数量不相加充当月度总量。
2. **读取已有周报历史**：已有简报的周报调用[历史比较模块](history.md)，传入当前完整配置、`target.json` 和执行目录；窗口包含目标周及之前七个完整自然周。已经取得的目标周响应直接交给该模块登记，其余期次按清单读取。
3. **接收历史结果**：接收模块返回的 `plan.json`、`statistics.json`、`charts.json` 及各期状态。历史阶段只查询已有结果；缺失、不可统计与真实错误按模块规则处理，不能通过补跑填满窗口。
4. **保留当期检查**：新建简报的首期月报同样读取已有历史，缺失月份保持缺失；新建简报的首期周报默认使用目标期资料，用户明确要求周报历史比较时执行同一模块。月报与周报均执行本期资料审核和全部高相关记录检查。
5. **完成图表维度选择**：按[独立图表模块](charts.md)调用维度选择流程，保存 AI 的字段角色、重要性顺序和业务理由；以实际字段 `level` 或 AI 重要性确定一个分类趋势，再按技术路线、产品线、其他技术字段选择公司交叉图。历史报告和只有当期资料的报告均使用本地选择文件生成 `charts.json`，继续交给步骤四。

### 步骤四：生成与交付

1. 使用 `monitor.py prepare-report`，传入当前完整配置原始响应、完整目标期原始响应及 `target.json`，保存带来源路径和 SHA-256 的 `report-inputs.json`；程序检查身份、日期和配置一致性。需要依据已有完整资料组织重点时，执行[重点规则模块步骤三](focus.md#步骤三判断本期资料的展示位置)，同时传入 `--focus` 和 `--review`。调用 [HTML 模块](html.md)，传入该输入文件及 HTML 输出路径。
   - 报告输入增加 `--charts <charts.json>`，历史文件采用模块实际返回的路径。目标期已有完整资料时必须提供 `--data`，保留本期全部内容和完整性检查；图表模块根据比较条件选择两个优先趋势图或实际范围分布，并在下方展示有真实资料的公司交叉图。
   - 仅查看且目标期缺失，或目标期没有可统计结果时，省略 `--data` 并提供图表文件；生成历史比较报告并明确目标月或目标周的实际状态，目标期明细生成状态保持未完成。全部历史均无可用结果时，只显示实际查询范围与状态。
2. 检查 HTML 脚本结果、设计校验、页面行为及打印显示；可以自行修正的问题在所属步骤修正并重新执行必要检查。
3. 按 [HTML 文件命名规则](html.md#步骤二自动生成)使用报告主题、日期范围和报告类型命名，交付脚本实际返回的 HTML 路径及目标日期。原始图片保持服务提供的安全 URL，图片显示需要网络；样式与交互代码内置。
4. 创建流程交接了持续跟踪要求时，核对[每周定时任务模块](schedule.md)的结果，补全尚未完成的任务创建，并分别交付本期报告与实际任务状态。用户只要求单次报告或查看已有结果时，按本次请求完成交付。

## 输出与完成条件

- 输出按主题、日期范围和报告类型命名的 HTML、同名 `.checks.json`、目标文件、原始配置和数据，以及最终执行状态。
- 只有数据身份与周期一致、全部高相关记录进入重点或明细、重点入选依据有原始证据、页面检查通过且 HTML 已交付时，报告任务完成。显示开关与目录条件均不能免除高相关完整性检查。
- 明确要求原始数据或 JSON 时交付取得的数据，并记录未生成 HTML 的用户要求。
- 历史比较报告记录实际查询窗口、有效和缺失期次、比较限制及图表来源；目标期未取得完整资料时，完成状态只表示历史报告已交付，不表示目标期明细生成完成。
