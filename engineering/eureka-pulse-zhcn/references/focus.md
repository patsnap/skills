# 重点规则与资料审核

## 目标、输入与输出

- **目标**：根据用户的监控问题确定值得进一步阅读、验证或跟进的资料，并完整保留其他高相关记录。
- **输入**：`requirements.json`、参数生成工具或最新完整配置、完整目标期原始响应。已有用户重点规则和资料限制继续保留。
- **规则输出**：`focus.json`，包含本次 `monitoring_objective` 与可直接用于 MCP 创建或更新的 `typical_filters`。
- **本期审核输出**：需要依据已有资料组织本期重点时保存 `focus-review.json`，通过来源路径、校验值、稳定记录 ID 和原文摘录引用原始响应。服务端返回的 `typical_tech_interpret` 始终保持原样。

## 步骤一：从监控问题确定规则

1. **明确分析目标**：读取用户关心的公司、技术、产品及用途，说明本期重点要帮助用户决定阅读哪些方案、开展哪些验证或跟进哪些事件。公司与产品范围已经明确时直接采用，不要求用户另选技术方向。
2. **确定分析维度**：技术资料围绕问题、作用对象、方案机制、效果与适用条件组织；产品或产业事件围绕对象、事件、时间、阶段与来源组织。只配置与本次范围有关的规则。
3. **确定证据与比较基准**：技术资料应有能够核实问题和机制、机制和效果等联系的原始证据；效果保留实验条件或预期性质。比较同一期同类资料的直接相关性、证据完整程度与代表性；历史变化依赖已经取得的可比历史。
4. **形成重点配置**：写入 `focus.json` 的监控目标，以及每项规则的 `key`、`name`、`data_scope`、`judgement`、`focus_guidance`、`output_guidance`、`card_fields`；需要比较基准时填写 `benchmark`。每项规则的 `ai_fields` 只保存所用全局字段的 `field_key` 字符串数组；字段名称、格式、枚举和提取要求统一定义在完整配置的全局 `ai_fields`。需要新提取字段时，按 MCP 当前 schema 在完整提交参数的全局 `ai_fields` 中定义，再由重点规则引用。字段均有明确阅读用途。
5. **检查规则是否可执行**：入选条件说明作用对象、证据充分性、判断方法和适用范围，输出说明如何回答监控问题。用户指定的限制保持原样。无监控用途的类别不增加。

## 步骤二：保存创建或修改参数

1. 使用 `monitor.py configure --input <参数原始响应> --focus <focus.json> --output <创建参数.json>`。程序开启 `detail_module.visible`，保留有效目录；缺少可显示模式时采用整体明细。
2. 参数生成工具已经提供完整且适用的重点规则时，可以直接采用并检查；缺少规则或内容不完整时，由 AI 根据步骤一补充。参数检查要求显示技术明细且重点规则非空。
3. 检查每项重点规则的字段引用能在完整提交参数的全局 `ai_fields` 中唯一找到，重复字段定义、重复引用、未知引用或引用类型无效时立即报错并指出规则与字段。按目标 Tool 的当前 schema 提交完整参数并读取核实结果。原始参数响应、提交参数和真实读取响应分别保存。

## 步骤三：判断本期资料的展示位置

1. **取得结果**：优先使用服务端已经执行重点规则并返回的完整分组解读，核对名称、资料类型与实际内容。
2. **审核已有完整资料**：用户要求重整历史报告，或本期完整资料尚未包含对应重点结果时，可以依据已取得的完整资料执行本步骤。分析和分组保存在独立审核文件中，页面说明其来源为本期资料审核。远程调用失败时完整记录失败，已经取得的有效资料仍可用于已授权的报告工作。
3. **覆盖全部高相关资料**：阅读本期全部 `score >= 4` 的技术记录，逐项确定与监控问题的联系；核实来源中的问题、机制、效果和实际作用对象。不能根据公司主业、标题或系列名称补充机型采用关系。
4. **选择代表性重点**：综合直接相关性、证据完整程度与不同技术方向覆盖，选择值得阅读或验证的方案；同类方案以具有不同作用机制或用途的资料为代表。技术重点来自已有高相关记录，评分保持服务原值。其他高相关记录完整进入明细。
5. **保存依据**：每条重点记录写明所属规则、稳定记录键、入选依据，以及至少两个不同原始字段的文字摘录。程序核实摘录确实存在于对应原始字段。结论区分公开方案、来源所述效果和待验证条件。
6. **处理无匹配资料**：没有满足条件的重点时，保存具体原因；资料缺失不代表公司没有活动。新闻缺失保持无匹配状态，不补造事件。

## 审核文件结构与交接

- **身份与来源**：`source=local_evidence_review`、真实 `pulse_id`、`period`、`data_source`（原始文件路径及 SHA-256）、`data_sha256`（业务对象校验值）、`focus_sha256`（规则校验值）。
- **审核范围**：`assessed_record_keys` 列出本期全部高相关技术记录，程序与原始结果逐项比较。
- **重点记录**：`selections[]` 包含 `focus_key`、`record_key`、`reason` 和 `evidence[]`。证据中的 `path` 使用 JSON 对象键及数组位置组成的数组，例如 `["item_info", "llm_innovation_list", 0]`；`quote` 保存该字段中的原文。
- **阅读标题**：可以为重点补充 `display_title`，根据已核实的作用对象与机制形成简短标题；原始标题完整保留在资料详情中。标题不能增加原文没有确认的效果或产品采用关系。
- **无入选结果**：`selections=[]` 时提供 `no_selection_reason`，说明实际证据不足或无匹配内容的原因。
- **报告交接**：调用 `monitor.py prepare-report`，增加 `--focus <focus.json> --review <focus-review.json>`。输入清单记录全部来源校验值，HTML 模块核实记录、证据与高相关覆盖后生成报告。
